# 第十二章 欠画申报与键盘激活

第十一章给渲染核心装上了只画欠画条带的能力，可整章下来没有人申报过欠画，六道判例里的脏区全是测试手工推进收集器的。这一章把申报接到真实的状态变化上：控件改了自己的状态，就顺手把欠画的区域推进清单。键盘也从一把钥匙长成三把，Tab 之外，Enter 和 Space 落到焦点持有者手里，复选框第一次能被键盘翻转。收尾是 `run_dirty`，事件、申报、条带重建在它身上合成规格说的那一轮完整管线。

## 欠画靠申报，不靠轮询

状态变了，谁欠画，这个知识在谁手里。三条路都摆一摆。

第一条是渲染侧自己比：重建前把缓冲和上一帧逐像素比一遍，不一样的才算欠。屏幕小的时候可行，可它有两个过不去的地方。一是每轮都付一次全屏比对的代价，就算什么都没变。二是条带模型下缓冲只装得下一条带，上一条带的内容早就被覆盖了，没有东西可比。

第二条是控件被问：渲染前挨个问「你这轮改过吗」。每个控件都得记一份「我改过没有」的状态，而这份状态只在被问到的那一刻才有用，问早问晚都作废。为了一个时机错误的问题，给每个控件添记录的负担。

第三条就是本章的方案：申报。状态改变的代码自己最清楚哪些像素受影响，它在改变发生的当场把区域推进收集器，渲染侧要重建时来问收集器。第十一章的收集器不用改一个字，它本来就是为这个角色准备的，缺的只是有人往里推。

## 申报通道：树上的一个指针

申报通道住在 `Widget` 上，一根指针加两个函数。

```cpp
/// Wires the repaint reporter for this whole subtree. Called once at tree
/// assembly, usually on the root; late-added children inherit it too.
void set_dirty_sink(DirtyRegions* sink) noexcept;

/// Reports an area as owing a repaint. State mutators call this as they
/// change; with no sink wired the report is dropped, which keeps widgets
/// usable in painter-only tests.
void invalidate(base::RectI area) noexcept {
    if (dirty_ != nullptr) {
        dirty_->push(area);
    }
}
```

`set_dirty_sink` 做的是接线，而且要接到整棵树上。它把指针存进自己，再沿着孩子走一遍，每个后代都存同一根指针。走树要递归，与 `draw` 同一个形状，同一条 `NOLINT` 加同一个理由（树的深度就是界面层级，界面层级是个位数，递归在这里不构成栈风险）。为什么存在每个控件身上，而不是只存根上一份、申报时再从自己往上爬？因为分发器把事件直接递到叶子手上，命中测试返回的就是最里层的控件，控件申报时手里只有自己。每次申报都爬一遍树去找根，不如接线时多走一遍、把指针送到每个人手里。

`add_child` 也参与接线。收养孩子的那个函数会把当前的指针传给孩子，整棵被收养的子树都跟着接上。于是接线的时机自由了：先接线后组装、先组装后接线，都能到达每一个人，晚到的孩子带着收养那一刻的指针。

`invalidate` 的判空是设计，不是疏忽。没人接线的控件把申报悄悄丢掉，跟第六章空宿主表提交无物可提交是同一个姿态：核心不假设外面一定有人接。第九章那些只拿画笔做测试的控件，一行不用改，行为与从前一字不差。断言或者报错在这里都是把「没人听」当成了故障，可它只是没人听。

## 谁在申报：三处现场

通道铺好了，剩下的问题是哪些代码该推。这一版有三处。

可见性是一处。`set_visible` 翻转时申报自己的边界，藏起来欠的是旧位置的恢复（后面的东西要露出来），亮出来欠的是新位置的绘制。翻转之外的情形不申报：函数开头多了一个早退，状态没变，像素就不会变，也就什么都不欠。这个早退是判例验过的行为，同一状态设两遍，清单里不会多出第二条。

焦点是一处。第十章说过，焦点环是框架的策略，画在持有者的边界上。策略是框架的，申报也就是框架的：`set_focused` 翻转时由它替控件申报边界，控件自己不用知道身上有一圈环。焦点挪动于是天然产生两笔申报，旧持有者交还，新持有者接住。同样的早退也在这里：已经是持有者的，再设一次什么都不发生。

控件状态是第三处。复选框和按钮在自己的事件处理里翻转状态，翻转的当场申报自己的边界。哪个控件欠哪块像素，只有控件自己知道，别人替它猜只会猜错。三处现场的分工由此清楚：可见性和焦点是 `Widget` 基类的代码，控件状态是控件自己的代码，两边用的都是同一个受保护的 `invalidate`。

## 键盘的另外两个名字

第十章给核心点名了 Tab，当时的理由是焦点遍历是树自己的语义，分发器必须认得。激活键是同一个论证再用两次：控件要能在不认识宿主的前提下认出自己的激活键，Enter 和 Space 就得有名字。

```cpp
inline constexpr std::uint32_t kKeyTab = 15;
inline constexpr std::uint32_t kKeyEnter = 28;
inline constexpr std::uint32_t kKeySpace = 57;
```

三个值都是 evdev 键码，PC 宿主把平台键码映射过来就是它们。其余键码照旧宿主定义、照旧不透明：控件可能收到，收到就忽略，从不解码。

分发器的那条 KeyDown 路由跟着长了一截：

```cpp
void deliver(Widget& root, const host::KeyDown& word) noexcept {
    if (word.code == host::kKeyTab) {
        static_cast<void>(root.advance_focus());
        return;
    }
    if (Widget* holder = root.focused_widget(); holder != nullptr) {
        holder->on_key_down(word.code);
    }
}
```

形状还是那句话：Tab 是树的语义，分发器留着；其余键码原样转交焦点持有者，核心不解码。没人持有焦点，键码照常被消耗、照常计数，只是没人收到。`on_key_down` 是 `Widget` 上的新虚函数，默认空函数体，与按下抬起一个待遇：不接输入的控件，什么都不做就是诚实的默认。

复选框第一个接住它。Enter 和 Space 翻转盒子，与指针按下完全一样，翻完申报自己的边界，下一轮重建把实心标记送出去。按钮不接，这是当批的明确决定：按钮是暂态控件，键盘激活按住 Enter 该显示按下的样子、松开再恢复，中间需要「按住的那几帧」，而那需要按键重复或者时钟节拍的故事，至今没有批次带来过。这段理由写在 `button.hpp` 的类注释里，判例把「Enter 打在聚焦的按钮上、`pressed` 仍是 false」按在测试里，将来节奏故事进场时，这个判例就是第一个要翻绿的。

## run_dirty：管线合龙

```cpp
template <typename CanvasT>
[[nodiscard]] int run_dirty(const host::HostTable& host, Widget& root, CanvasT& strip,
                            base::SizeI screen, DirtyRegions& dirty) noexcept {
    int consumed = 0;
    host::Event event;
    while (host::try_poll_event(host, event)) {
        ++consumed;
        dispatch_event(root, event);
    }
    render_strips(root, strip, screen, host, dirty);
    dirty.clear();
    return consumed;
}
```

三步，处理事件、重画被点名的条带、清空收集器。返回值是这轮消耗的事件数，没人要的键也算被消耗过。

两个口径要说清。第一帧是调用者的活：这个循环只重画申报点名的区域，没人申报过初始画面，所以上手先拿 `render_strips` 整幅画一遍，或者把整个屏幕推进收集器，然后才轮到 `run_dirty` 接手。清空放在重建之后：欠的像素已经送到宿主上，这一轮的债不进下一轮。收集器因此是单轮的临时状态，不是越积越厚的历史，谁也不欠谁的。

`run_once` 原样保留。全帧重画靠「画得全」保正确，第九章立它的时候是简化，现在它是对照：两条路径共享同一个 `render_window` 原语，差别只在窗口怎么开。判例七会把两条路径的提交次数并排放着，经济差当场可见。

## 判例

三组判例各守一段。

`widget_tests` 守接线。接线后的申报进清单，整棵子树都够得着；晚收养的孩子带着接好的线，申报照进；同一块区域申报两遍，合并成一条，不翻倍；状态没变的 `set_visible` 什么都不申报。这里有个推导时差点摔的地方：两块相同的矩形推进收集器会合并，包围盒还是它自己，条数是一不是二。指望「推两次、数两条」的断言会平白多红一次，判例里每一处数条的断言都按合并语义算过。

`run_loop_tests` 守键盘。Tab 把焦点送到复选框，Enter 翻转它，提交的帧里有实心标记；Space 翻回去；一个谁也不认的键码（判例里用 42）穿过整棵树什么也不改。Enter 与 Space 分在两轮验是有意的：合在一轮里，若两个键都没翻转，终态与初态相同，断言分不出「都生效」和「都没生效」，分两轮各自看像素，谁失职谁翻红。空树的 Enter 被消耗、无人接收，按钮的 Enter 被按在「不激活」上。

`render_tests` 的判例七守整条管线的经济。亮底全屏一块复选框在条带 0、一个按钮在尾条带，先手工整幅铺第一帧，提交三次。然后是三轮 `run_dirty`：

- Tab 加 Space：焦点申报与翻转申报是同一块区域，合并成一条，只重画条带 0，提交数 3 变 4，清单清空，标记与焦点环的像素都在。
- 再一个 Tab：交还环的申报在条带 0，接住环的申报在尾条带，两条互不相交，重画条带 0 和 2、跳过条带 1，提交数 4 变 6。环挪走了的像素（按钮角变暗、盒子角复原）和保留的标记一起验。
- 空轮：没有事件，没有申报，提交数停在 6。经济路径的全部意义就在这一轮，什么都不欠就什么都不送。

像素层与次数层照旧两层一起断：次数证明工作去了该去的地方，像素证明画出来的东西是对的。

## 验收

红绿实验做两处，各验管线的一段神经。

第一处验清空。打开 `include/visor/ui/run_loop.hpp`，把 `run_dirty` 末尾的 `dirty.clear();` 注释掉，这一轮的欠画不再退休。重建跑测试，两处红：判例七里「重建后清单清空」的断言先红，紧接着空轮的提交数断言红，欠着旧账的清单让什么都没发生的空轮又送了一轮像素。复原，绿。

第二处验申报。打开 `src/ui/widgets/widget.cpp`，把 `set_focused` 里的 `focused_ = on;` 注释掉，焦点从此翻不动。重建跑测试，红得比第一处宽：焦点状态是核心状态，第十章的焦点遍历判例、焦点环像素判例全跟着红，判例七的焦点环像素与提交次数也在其中。看完都复原，全绿。
